IMPORTANT
---------
This document supersedes the earlier visual direction in which purchases expanded inline inside /access rows.

The completed Phase 2 and Phase 3 engineering work should be preserved where applicable:
- backend-driven pricing and plan lookup
- validated purchase targets
- required bundle-module counts
- native radio semantics
- native checkbox semantics
- Pick 3 progressive-disclosure logic
- duration-reset logic
- payment-attempt scoping
- duplicate Paystack-start protection
- safe returnTo handling
- friendly payment errors
- server-side verification
- payment history and receipt logic

The major change is PRESENTATION and INFORMATION ARCHITECTURE.

OLD DIRECTION
-------------
/access row -> expands inline -> duration/configuration -> payment CTA

NEW DIRECTION
-------------
/access stays stable -> user chooses Unlock/bundle -> shared Purchase Modal -> Configure -> Review -> Paystack

The Access page is not a checkout surface anymore.

The Access page shows:
1. current access status
2. bundle opportunities
3. module ownership and availability
4. payment history

The Purchase Modal handles:
1. purchase configuration
2. duration selection
3. review
4. Paystack handoff

======================================================================
3. DESIGN PRINCIPLES
======================================================================

The visual system must remain PromotionSure-native. Research validates interaction principles; it does not import Apple, Material, Stripe, Linear, or another brand.

A. PURPOSE
Each surface has one job. /access manages access. The modal configures a purchase. Review confirms it.

B. HIERARCHY
Use typography, order, spacing, grouping, weight, alignment, and restrained color before adding decoration.

C. PROGRESSIVE DISCLOSURE
Do not show a decision before the user can meaningfully make it. Pick 3 is modules -> duration -> Review.

D. PREDICTABILITY
Selecting a radio selects the radio. It must not unexpectedly auto-advance. The user explicitly presses Review purchase.

E. VISUAL STABILITY
Opening a purchase must not cause /access to grow hundreds of pixels or move all content below it.

F. RESTRAINT
Green is an accent/action color, not structural scaffolding.

G. DIRECTNESS
The user should immediately understand what is owned, purchasable, coming soon, included, and charged.

H. RESPONSIVENESS
Mobile is composed deliberately; desktop is not merely shrunk.

I. ACCESSIBILITY
Prefer native controls, visible focus, comfortable targets, reflow, and state cues beyond color.

J. FINANCIAL CONFIRMATION
Use Review before Paystack so the user can confirm product, duration, selected modules where relevant, and total.


======================================================================
4. FINAL /ACCESS HIERARCHY
======================================================================

Normal order:
1. Page header
2. Payment needs attention, only when a genuine unresolved payment requires action
3. Bundle offers
4. Modules
   A. Unlocked
   B. Available to unlock
   C. Coming soon
5. Payment history

Why bundles come first:
- broad purchase choices should be visible before granular individual unlocking
- the page header already acknowledges current ownership first
- inside Modules, ownership is still shown before available-to-unlock rows

So the page does NOT begin with a sales card. It begins with status, then broader options, then module management.

======================================================================
9. BUNDLE OFFERS: PURPOSE AND VALUE
======================================================================

Bundle offers are the first normal content section.

They communicate two broader-access options:
- 3-Module Bundle: choose the required number of available modules
- Complete Module Bundle: access all currently available modules covered by the current plan

Create value through clarity, not sales decoration.

The user should instantly understand the difference between:
"I want a few modules"
and
"I want everything currently available."

18. SHARED PURCHASE MODAL: ROLE
======================================================================

This is a Purchase Modal, not the card-payment gateway itself.

Its job:
CONFIGURE -> REVIEW -> HANDOFF TO PAYSTACK

It should be a focused task surface, not a mini pricing website.

Modes:
- module
- pick3
- complete

All modes share the same shell, focus system, DurationSelector, Review component, CTA states, errors, and payment handoff.


======================================================================
19. TWO-STEP PURCHASE MODEL
======================================================================

Only two logical steps:
1. Configure
2. Review

Do NOT build:
Step 1 modules -> Step 2 duration -> Step 3 review

For Pick 3, module selection and duration are both part of Configure, using progressive disclosure.

Do not use a large visual wizard stepper. If orientation is useful, a quiet "1 of 2" / "2 of 2" near the heading is enough. It may be omitted if the transition is self-explanatory.

- add heavy shadow

37. URL / MODAL STATE ON /ACCESS
======================================================================

Preserve the Phase 2 validated query contract, but change what it controls.

/access
= no purchase modal

/access?module=<valid-purchasable-slug>
= module Purchase Modal open

/access?scope=pick3
= Pick 3 Purchase Modal open

/access?scope=complete
= Complete Purchase Modal open

Invalid module or scope
= no modal

The query controls modal visibility rather than inline row expansion.

Browser behavior:
/access -> Unlock Pension -> /access?module=pension -> modal opens
Back -> /access -> modal closes
Forward -> /access?module=pension -> modal reopens

Switching module -> Pick 3 -> Complete updates URL accordingly. Back/Forward restores the correct modal mode.

Do not reintroduce stale duplicate local expansion state.


======================================================================
38. PURCHASE ENTRY FROM OTHER PAGES
======================================================================

The user should not navigate through /access merely to unlock a module.

Dashboard stays Dashboard underneath the modal.
Practice stays Practice underneath the modal.

Recommended conceptual architecture:

openPurchase({
  mode: "module",
  moduleSlug,
  returnTo
})

openPurchase({ mode: "pick3", returnTo })
openPurchase({ mode: "complete", returnTo })

Use one PurchaseModalHost/Controller at an appropriate authenticated-app level.

For /access, hydrate it from the existing validated query contract.
For other pages, use the router/history/modal state that best fits the current app without forcing navigation to /access.

If global deep-linkable modals are desired later, design one consistent global URL contract instead of improvising a different query syntax on every page.

39. RETURNTO
======================================================================

Examples:
- Dashboard unlock -> pay -> return to safe Dashboard context
- /access unlock -> pay -> return to /access
- locked practice -> pay -> return to the relevant safe context when valid

Never permit arbitrary external return URLs.


======================================================================
40. MODAL FOCUS AND CLOSE
======================================================================

On open:
- remember trigger when possible
- focus modal heading or first meaningful control
- trap focus inside
- background content becomes non-interactive

On close:
- restore focus to exact triggering Unlock/bundle action when possible
- parent scroll position remains stable

Escape closes when safe.
Backdrop dismissal follows current product modal behavior.

No focus should be hidden behind sticky footer or viewport edge.


======================================================================
41. STEP TRANSITION AND MOTION
======================================================================

Configure -> Review should be direct.

Allowed:
- subtle body fade/slide
- restrained height adjustment
- heading update

Avoid:
- giant wizard animation
- card scaling
- bouncing CTA
- animated prices
- dramatic morphs

Respect prefers-reduced-motion.


======================================================================
42. REVIEW CHANGE BEHAVIOR
======================================================================

"Change" returns to Configure and preserves:
- module mode: duration
- Pick 3: selected modules + duration
- Complete: duration

Do not reset a valid purchase just because the user wants to inspect/edit it.


======================================================================
43. PAYMENT CTA, LOADING, ERROR
======================================================================

Use explicit copy:
Review purchase ->
Continue to payment
Preparing payment...

Do not use vague Proceed/Next/Continue for Paystack handoff.

On Continue to payment:
- synchronous duplicate-start guard activates
- one Paystack initialization only
- CTA becomes Preparing payment...
- relevant controls are protected from duplicate submission

On initiation error:
- keep modal open
- keep selected duration/modules
- show inline friendly error near payment footer
- role="alert" where appropriate
- no toast-only failure for the core transaction action

Example:
We could not start payment right now. Please try again.

Do not create a giant error card.


======================================================================
44. STALE / ALREADY-PAID STATE
======================================================================

A stale UI may still show Unlock after access has changed.

Current trusted backend logic remains authoritative.

If backend indicates access is already active:
- do not initialize another unnecessary payment
- refresh access state
- communicate/update modal appropriately

Do not trust only frontend display state for purchase eligibility.


======================================================================
45. PRICING RULES
======================================================================

Never hard-code:
- price
- currency
- duration
- savings
- bundle required count
- complete module count

Sample numbers in sketches are illustrative only.

Bundle page "From NGN X" must use the lowest valid currently available price for that bundle. Do not assume 1 month always exists or is always cheapest.

If plan data is unavailable:
- no fake price
- no broken enabled purchase action

Savings are secondary and only shown when actual pricing logic provides a meaningful value.

Never hard-code "all 9 modules". Use runtime counts and "currently available modules" language.
